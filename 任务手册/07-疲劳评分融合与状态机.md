# 🧮 阶段 6：疲劳评分融合与状态机

> **本阶段目标**：理解多特征融合评分的设计思路，验证三级状态切换逻辑。
>
> ⏱️ 预计时长：30 分钟 | 💻 你负责运行 + 验证评分合理性

---

## 🎓 你将学到什么

| 知识点 | 说明 |
|------|------|
| **多特征融合** | 为什么不能只靠一个指标？单一特征可能误报，融合多个证据才可靠 |
| **加权评分 vs 规则引擎** | 简单的"满足条件就加分"模式，可解释性最强 |
| **状态机 (FSM)** | 有限状态自动机——如何管理状态切换，防止来回抖动 |
| **防抖与冷却** | 为什么报警后要等几秒才能再报？避免连续"轰炸"用户 |

### 深入理解：为什么需要融合？

```
单一 EAR 判断：
  闭眼 → 疲劳？不一定！（可能在看仪表盘、强光眯眼）
  
多特征融合：
  EAR ↓ + MAR ↑ + Pitch ↑ + PERCLOS ↑ → 非常可能是疲劳
  EAR ↓ 但其他正常 → 可能只是眯眼看东西
```

论文中也证实了这一点（Ji 2004）：

| 证据组合 | 疲劳概率 |
|------|:--:|
| 无任何证据 | 57% |
| 仅 PERCLOS 异常 | 86%（仍不够） |
| PERCLOS + 头部点头 | > 95% ✅ |
| 三种以上视觉线索同时异常 | 接近 100% |

### 评分规则设计

```
疲劳分数 = 0  (每帧从 0 开始累加)

if 连续闭眼 > 0.5s:  +2
if 连续闭眼 > 2s:    +4
if PERCLOS > 阈值:   +3
if 检测到哈欠:       +2
if 1min 内哈欠 > 2:  +3
if 低头 > 2s:        +2
if Yaw 偏离 > 30°:   +1

总分 → 0~2: 正常  3~5: 风险  ≥6: 报警
```

### 状态机逻辑

```
         连续3s分数≥3          连续2s分数≥6
  NORMAL ──────────→  RISK  ──────────→  ALERT
    ↑                   │                    │
    │   连续5s分数<3      │   连续10s分数<6     │
    └───────────────────┘                    │
    └────────────────────────────────────────┘
```

**关键设计**：
- 升级需要**连续**满足条件（防抖动）
- 降级需要更长时间（防来回切换）
- ALERT 触发后有冷却期（防连续骚扰）

### 步骤 2：模拟不同疲劳等级

| 场景 | 操作 | 预期分数范围 | 预期等级 |
|------|------|:--:|:--:|
| 🟢 正常驾驶 | 自然面对摄像头 60s | 0~2 | NORMAL |
| 🟡 轻度疲劳 | 偶尔闭眼 2s + 偶尔低头 | 3~5 | RISK |
| 🔴 严重疲劳 | 持续闭眼 + 打哈欠 + 低头 | 6+ | ALERT |

### 步骤 3：验证状态切换逻辑

专门测试以下情况：

- [ ] NORMAL → RISK：分数连续 3s ≥ 3 后切换
- [ ] RISK → ALERT：分数连续 2s ≥ 6 后切换
- [ ] ALERT → RISK：恢复正常 10s 后降级（不立即降）
- [ ] 偶尔抖动不会触发（单帧高分不会立即升级）

### 步骤 4：调整评分权重

如果发现某个特征"太过灵敏"或"太迟钝"，改 `config.py` 中的分数：

```
例：你觉得低头不应该加 2 分，太敏感了
→ 改 HEAD_DOWN_SCORE = 1

例：你觉得连续闭眼 2s 应该更严重
→ 改 EYE_CLOSED_2S_SCORE = 6
```

## 🔧 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 分数一直很高 | 某个子模块阈值太低 | 逐模块排查，调高对应阈值 |
| 从不触发 ALERT | 评分上限太低 | 增大各项 `_SCORE` 值 |
| 频繁在 NORMAL/RISK 间跳动 | 切换时间窗口太短 | 增大连续判断的秒数 |
| 报警后很快就又报警 | 冷却时间太短 | 增大 `ALERT_COOLDOWN_SEC` |
