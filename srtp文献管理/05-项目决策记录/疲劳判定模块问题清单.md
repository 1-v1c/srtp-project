## 0. 当前阶段判断

### 初步结论

当前不建议把 **YOLO 目标检测 + 自写疲劳规则** 作为疲劳判定主线。

更合理的主线是：

```text
摄像头视频帧
↓
人脸关键点 / ROI 提取
↓
眼部状态 + 嘴部状态 + 头部姿态
↓
时间窗口统计
↓
疲劳等级 / 报警逻辑
```

其中：

- **眼部**：优先考虑 EAR / PERCLOS / 闭眼时长，或眼部 ROI + CNN 二分类。
- **嘴部**：优先考虑 MAR 判断打哈欠。
- **头部**：可用 MediaPipe + solvePnP 得到 Pitch / Yaw / Roll。
- **YOLO**：更适合做辅助模块，如手机、手部、安全带、分心行为检测，而不是疲劳判定主模块。

## 2. 技术路线决策：从 YOLO 主线转向疲劳特征融合

### 原先想法

```text
YOLO 检测眼睛/嘴巴/头部
↓
自己写规则判断疲劳
```

### 现在发现的问题

- YOLO 输出的是目标框和类别，不是疲劳状态。
- 疲劳是一个**时间状态**，不能只靠单帧检测。
- 眼睛闭合、打哈欠、点头都需要持续时间和频率统计。
- 如果只用 YOLO 检测 closed_eye / open_mouth，会遇到：
  - 小目标检测难；
  - 眼睛区域很小，定位不稳定；
  - 标注成本高；
  - 仍然需要另写时间逻辑。

### 更合适的主线

```text
MediaPipe / Dlib 提取面部关键点
↓
眼部：EAR / PERCLOS / CNN 眼部 ROI
嘴部：MAR
头部：Pitch / Yaw / Roll
↓
时间窗口统计
↓
疲劳判定规则 / 疲劳评分
```

## 3. 疲劳判定模块需要尽快回答的问题

### 3.1 输入采集问题

- 我们使用普通 RGB 摄像头，还是 NIR 夜视摄像头？
- 如果使用 RGB 摄像头，夜间、暗光、逆光是否还能稳定识别人脸关键点？
- 如果使用 NIR 摄像头，预算和安装方式是否可接受？
- 摄像头安装位置是仪表台、方向盘后方，还是显示器上方？
- 是否需要考虑眼镜反光、口罩、遮挡、低头等情况？

### 3.2 人脸关键点方案问题

- 使用 MediaPipe Face Mesh 还是 Dlib 68 点？
- MediaPipe 是否能在我们的电脑/开发板上稳定实时运行？
- 如果头部转动或低头，眼部 ROI 是否会丢失？
- 是否需要像 Sensors 2024 那样做眼部 ROI 修正？
- MediaPipe 是否同时用于：
  - 眼部 ROI；
  - 嘴部 MAR；
  - 头部姿态 Pitch / Yaw / Roll？

### 3.3 眼部疲劳判定问题

需要决定眼部采用哪种方案：

| 方案 | 优点 | 缺点 | 当前倾向 |
|---|---|---|---|
| EAR 阈值 | 实现简单、可解释、无需训练 | 对眼镜、角度、个体差异敏感 | 适合作为 baseline |
| PERCLOS | 疲劳检测经典指标，有文献支持 | 需要时间窗口统计，依赖眼睛开闭稳定检测 | 强烈建议保留 |
| 眼部 ROI + CNN | 可能比单纯阈值鲁棒 | 需要数据集和训练/迁移，复杂度更高 | 可作为进阶方案 |
| YOLO 检测 open_eye/closed_eye | 统一检测框架 | 眼睛小目标难、标注成本高 | 不建议作为主线 |

需要继续确定：

- 闭眼阈值是多少？
- PERCLOS 时间窗口取 30s、60s，还是更短？
- 连续闭眼多长时间触发报警？
- 是判断“闭眼”还是判断“drowsy/not drowsy”？

文献参考：

- Ji 2004：PERCLOS 是有效眼部疲劳参数，并与反应时间相关。
- Bergasa 2006：PERCLOS 用 30s 窗口统计，并和其他参数融合。
- DriCare 2019：闭眼帧比例、连续闭眼时间、眨眼频率共同判断。
- Sensors 2024：眼部 ROI 经 CNN 判断 drowsy 概率，超过 95% 且闭眼超过 300ms 触发报警。

### 3.4 嘴部打哈欠判定问题

当前更倾向用 **MAR**，不建议用 YOLO 单独检测 yawn。

需要回答：

- MAR 阈值如何设定？
- 是否需要针对不同人做个体化校准？
- 张嘴说话、唱歌、笑，会不会被误判为哈欠？
- 是否需要加入持续时间判断？
- 是否统计 1 分钟内打哈欠次数？

文献参考：

- DriCare 2019：嘴部高宽比阈值约 0.6，并统计 7s 内张嘴帧比例；1 分钟内打哈欠超过 2 次判为疲劳。
- Sensors 2024：MAR 阈值通过试验设为 55，并要求超过阈值持续至少 5s 才触发报警。

### 3.5 头部姿态问题

头部姿态不应该忽略。建议把它作为第三类辅助特征。

需要回答：

- 是否用 MediaPipe Face Mesh + OpenCV solvePnP 计算头部姿态？
- 是否分成三个角度：
  - Pitch：低头 / 抬头；
  - Yaw：左转 / 右转；
  - Roll：歪头；
- 哪些姿态属于疲劳，哪些属于分心？
- 低头持续多久算疲劳/分心风险？
- 长时间偏头是否单独归为注意力不集中，而不是疲劳？

可参考：

- Bergasa 2006：使用脸部朝向、点头频率和固定凝视作为疲劳/注意力下降特征。
- Ji 2004：将头部运动和眼部、凝视、表情一起做概率融合。
- Sensors 2024：未来工作中也提出加入 head pose estimation。

### 3.6 疲劳等级与融合逻辑问题

需要决定最终输出不是简单“疲劳/不疲劳”，而是：

```text
正常 / 轻度疲劳 / 中度疲劳 / 严重疲劳 / 分心驾驶
```

或简化成：

```text
正常 / 风险 / 报警
```

可选融合方式：

| 方式 | 优点 | 缺点 | 适合阶段 |
|---|---|---|---|
| 阈值规则 | 简单、可解释、易展示 | 阈值需要调参 | 第一版实现 |
| 加权评分 | 可融合多个特征 | 权重主观，需要实验验证 | 推荐第一版使用 |
| 模糊逻辑 | 适合处理不确定性，文献支持 | 实现略复杂 | 第二版优化 |
| 贝叶斯网络 | 能建模概率关系 | 对本科项目可能偏复杂 | 综述/展望 |
| 端到端深度模型 | 精度可能高 | 数据需求大、解释性弱 | 暂不推荐 |

## 4. 当前推荐的第一版疲劳判定方案

### 4.1 输入

```text
摄像头视频帧，优先 RGB 摄像头验证；条件允许时换 NIR 摄像头。
```

### 4.2 处理流程

```text
视频帧
↓
MediaPipe Face Mesh
↓
提取眼部关键点、嘴部关键点、头部关键点
↓
眼部：EAR / 闭眼帧 / PERCLOS
嘴部：MAR / 打哈欠持续时间 / 打哈欠次数
头部：Pitch / Yaw / Roll
↓
疲劳评分
↓
正常 / 风险 / 报警
```

### 4.3 第一版暂定指标

| 模块 | 指标 | 说明 |
|---|---|---|
| 眼睛 | EAR | 判断单帧眼睛开闭 |
| 眼睛 | PERCLOS | 判断一段时间内闭眼比例 |
| 眼睛 | 连续闭眼时间 | 捕捉微睡眠 / 长时间闭眼 |
| 嘴巴 | MAR | 判断嘴巴张开程度 |
| 嘴巴 | 打哈欠持续时间 | 避免把说话误判为哈欠 |
| 头部 | Pitch | 低头/点头检测 |
| 头部 | Yaw | 长时间不看前方 |
| 头部 | Roll | 歪头异常姿态 |

### 4.4 第一版示例规则

> 下面只是初始规则，后续需要用实验数据调参。

| 条件 | 风险分 |
|---|---:|
| 连续闭眼超过 0.5s | +2 |
| 连续闭眼超过 2s | +4 |
| 30s 内 PERCLOS 超过阈值 | +3 |
| MAR 超过阈值并持续 3–5s | +2 |
| 1min 内打哈欠超过 2 次 | +3 |
| Pitch 低头持续超过 2s | +2 |
| Yaw 长时间偏离正前方 | +1 或归为分心 |
| 检测到手机/手离方向盘等 YOLO 扩展目标 | 分心驾驶单独报警 |

疲劳等级：

```text
0–2：正常
3–5：风险
≥6：报警
```

## 5. YOLO 在项目中的重新定位

### 不建议

不建议让 YOLO 直接承担：

- 眼睛开闭主判定；
- 打哈欠主判定；
- 疲劳等级主判定。

原因：

- 眼睛/嘴巴是小目标，YOLO 检测稳定性可能不如关键点方法。
- YOLO 需要大量框标注。
- 疲劳判断依赖时间统计，而不是单帧目标检测。

### 建议用途

YOLO 可以用于扩展检测：

- 手机；
- 手部；
- 安全带；
- 方向盘区域；
- 驾驶员是否在位；
- 车内异常物体。

重新定位为：

```text
疲劳判定主线：MediaPipe + EAR/PERCLOS + MAR + Head Pose
安全行为扩展：YOLO
```

## 6. 需要补充验证的实验

### 6.1 可行性验证

- MediaPipe 能否稳定检测驾驶员面部？
- 戴眼镜时关键点是否稳定？
- 低头、转头时眼部和嘴部关键点是否丢失？
- 普通 RGB 摄像头在弱光下是否可用？

### 6.2 指标验证

- EAR 阈值是否需要因人而异？
- MAR 阈值是否需要因人而异？
- PERCLOS 窗口取 30s 是否太长？是否需要 10s/15s 快速预警窗口？
- 低头和正常看仪表盘如何区分？

### 6.3 系统验证

- 能否达到至少 10 FPS？
- PC 端和嵌入式端速度差异多大？
- 报警延迟能否控制在 1–2s 内？
- 是否会频繁误报？

## 10. 当前暂定项目路线

```text
第一阶段：PC 端实时原型
MediaPipe Face Mesh
+ EAR/PERCLOS
+ MAR
+ Pitch/Yaw/Roll
+ 简单疲劳评分

第二阶段：提升鲁棒性
眼部 ROI 修正
+ 个体化阈值
+ 误报/漏报分析

第三阶段：扩展人车协同安全
YOLO 检测手机/手部/安全带
+ 疲劳状态融合
+ 报警与交互界面
```

当前建议：

> 先把疲劳判定模块做成“可解释、可实时、可演示”的系统，再考虑引入 YOLO 和 CNN 增强。不要一开始就陷入复杂模型训练。
